# 질문·답변 챗봇 개발 문서

## 구성

| 파일 | 역할 |
| --- | --- |
| `server.py` | 로컬 HTTP 서버·질문 검증·질의응답 라우팅 |
| `maintenance.py` | 부품명 검색·정비 안내·원문 및 그림 렌더링 |
| `service_guides.py` | 교범 버전·페이지 근거 검사와 검토 요약 구성 |
| `data/service-guides.json` | 12종 부품의 설명·점검·정비·주의사항·그림 범위 |
| `data/parts.json` | 부품 ID·별칭·SGN·문서 및 페이지 연결 |
| `web/app.js` | 질문 전송·답변 및 그림 표시·원문 모달·참고 문서 |
| `web/style.css`, `web/guides.css` | 반응형 채팅 화면과 정비 안내 스타일 |
| `scripts/import_manuals.py` | 허가된 로컬 PDF의 선별 색인 생성 |

질문 입력과 답변 표시가 기본 화면입니다. 카메라·비전 모듈, 모델 가중치 설정, 영상 스트림·프레임 전송과 이미지 인식 API는 제거했습니다. 답변의 사진은 교범 내부의 검토된 그림을 표시하는 기능입니다.

## API

| 메서드·경로 | 용도 |
| --- | --- |
| `POST /api/chat` | 질문과 최근 대화로 답변 생성 |
| `GET /api/status` | 기존 제안서와 선택적 로컬 텍스트 모델 설정 상태 |
| `GET /api/parts` | 부품 목록과 색인 쪽수 |
| `GET /api/part?id=battery` | 해당 부품의 페이지 및 공통 주의사항 |
| `GET /api/manuals` | 교범 목록·쪽수·가용 여부; 로컬 절대 경로는 제외 |
| `GET /api/pages` | 기존 개발 제안서의 쪽별 요약 |
| `GET /manual-page?doc=engine&page=572` | 원본 페이지 PNG |
| `GET /manual-figure?part=battery&figure=location` | 고정된 허용 영역의 교범 그림 PNG |
| `GET /document?doc=engine` | 등록된 로컬 교범 PDF |
| `GET /document` | 선택적 `data/source.pdf` 제안서 |

질문 요청은 `question` 문자열과 선택적 `history`, `partId`입니다. 질문은 1~2,000자, 전체 본문은 24,000바이트 이하입니다. `history`는 최대 12개 메시지이며 각 `content`는 4,000자 이하입니다. UI는 최근 메시지 6개를 전송합니다. 정비용 `partId`는 API 호환을 위해 유지하지만 UI에서 별도 부품 선택을 요구하지 않습니다.

응답은 `answer`, `sources`, `mode`, 선택적 `notice`를 포함합니다. 검토된 정비 안내는 `presentation: "service-guide"`와 `guide`를 추가합니다. `guide`는 설명, 점검 및 정비 단계, 주의사항, 그림, 추가 확인 질문으로 구성됩니다. 원문은 기본 답변에 복사하지 않고 필요 시 출처 모달에서 열 수 있습니다.

정비 출처의 `id`는 `문서ID:PDF쪽`이며 각 문장의 `refs`와 대응합니다. `answer`는 같은 요약의 텍스트 버전으로 대화 이력에 사용합니다. 사용자가 명시한 부품명·별칭·SGN으로 부품을 찾고 지원하는 후속 질문에는 이전 부품 문맥을 활용합니다. 일반 증상만으로 모든 고장을 진단하는 기능은 아닙니다.

## 자료와 그림

교범 원본은 기존 로컬 경로에 두고 가져오기 시 경로·쪽수·SHA-256을 등록합니다. 생성한 `*.local.json`, PDF, 임시 이미지는 Git 추적에서 제외됩니다. 파일을 옮기거나 교체하면 다시 가져오고 서버를 재시작합니다.

요약은 가져온 교범의 SHA-256 메타데이터와 필요한 근거 페이지를 검사합니다. 원본 파일 전체의 해시를 매 요청마다 다시 계산하지는 않습니다. 버전·페이지가 맞지 않으면 검토 요약을 제공하지 않습니다. 규정값과 전체 선행/후속 작업은 원문 확인이 필요합니다.

그림 API는 등록된 부품·그림 ID만 받고 사용자가 지정한 파일 경로나 자르기 좌표는 받지 않습니다. PDF 렌더링 후 검토된 영역을 잘라 표시하며 서버 메모리에 최대 32개를 캐시합니다. 원본 전체와 캡션·페이지를 연결하고, 그림 로딩 실패 시 원문 열기로 대체합니다.

## 실행·검증

README의 설치·자료 가져오기·실행 절차를 따릅니다. `PORT`는 기본 8000, `OLLAMA_MODEL`은 기존 제안서용 선택적 로컬 텍스트 모델입니다. `.env` 자동 로딩은 없습니다. 정비 안내 자체에는 생성 모델이 필요하지 않습니다.

```powershell
python -m unittest discover -s tests -v
```

서버는 `127.0.0.1`에만 바인딩합니다. 대화는 브라우저 메모리에만 보관하며 새 대화·새로고침에서 초기화됩니다. 인증·TLS·운영용 접근 제어·다중 사용자 격리는 별도 구현 사항입니다.


### 질문 범위 및 근거 확인 (2026-10-30)

- 차량 정비·군학연계 자료 외 질문: 범위 밖 안내 (`reason: out-of-scope`).
- 차량 관련이지만 검토된 안내로 답할 수 없는 질문: 근거 부족 안내 (`reason: missing-evidence`). 두 경우 모두 출처와 정비 안내를 생성하지 않습니다.
- 부품명·SGN만 일치한다고 안내하지 않습니다. 질문 전체가 일반 설명·위치·점검·교환 등 허용된 요청 형태인지 확인합니다. 헤드램프 결로는 별도로 검토된 안내를 사용합니다.
- 수치, 가격, 교환 주기, 미검토 증상, 다른 부품을 섞은 질문은 추측하지 않습니다. 정비 PDF 전체를 의미적으로 판정하는 모델이 아니라 보수적인 규칙 방식이므로, 표현이 낯설면 근거 부족으로 처리될 수 있습니다.
- 이전 질문이 지원되는 경우에만 명확한 후속 질문에 부품을 이어받습니다. 기존 제안서 검색은 명시적인 제안서 주제에 한해 유지합니다.
- 검증: Python unittest 32개 통과. 범위 밖 질문, 부품명 포함 무관 질문, 미지원 수치·가격·증상, 명시 partId와 대화 이력을 통한 우회, 기존 안내의 출처 연결을 확인했습니다.
